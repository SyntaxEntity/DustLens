## 0. 一句话

> **DustLens 是一个「目录整洁度诊断器」：它只声明形式属性、附上引用证据，
> 把「需不需要」的判断权完整交给用户，并用 LLM 回答「这是什么」。**

## 1. 核心定位

### 1.1 与简报的关系（这是一次目标修正）

简报从一次「`df` 掉了 66 G」的真实清理事件倒推需求，**默认目标是释放空间**。
本次讨论把它修正为：

> ## ✅ 整洁是目的，空间是副产品。

**理由**：这个修正改变了整个排序逻辑。135 G 的 Steam 库是**整洁的**（大、规范、有主、有引用）——
按「省空间」它是头号目标，按「整洁」它不该出现在第一屏。

**这不是否定简报**，而是找到了简报那些案例的真正共性。简报的洞察（「必须鉴定，不能只匹配规则」）在「整洁」框架下依然成立，而且更自洽。

### 1.2 「脏」从哪来：三类污染源

| 污染源 | 典型表现 |
| --- | --- |
| **用户自己没意识** | 下载乱丢、解压后归档与解压目录并存 |
| **agent / 自动化乱开** | 构建产物、缓存、临时工作目录遍地 |
| **流氓软件拉屎** | 卸载后残留、自建目录不清理、无视桌面环境规范 |

> **注意**：用户对「不合规」的态度是**长期点名**——「你不遵守规范我们就一直把你列出来」。
> 定位是**记账**，不是**修复**。

### 1.3 目标用户（隐含确定）

观点：「**不关心不等于不重要，每个人都需要关注起来，不是他们不关心，只是他们没有认知到。**」

> **这意味着产品的核心工作是「让人看见」，而不是「替人做决定」。**

**待确认**：XDG 规范审计 + 目录整洁，天然偏向 Linux 开发者与运维；
而「微信拉屎」的受害者更偏普通桌面用户。两者需求不完全重叠，**这仍是未解决的最大未知**（对应简报 R1）。

## 2. 不定项（Iron Rules）

以下原则是本次讨论的核心产出，**任何功能设计不得违反**：

| # | 原则 | 理由 |
| --- | --- | --- |
| **P1** | ✅ **工具只声明形式属性，并附上引用证据；价值判断永远由用户完成，工具不代劳、也不暗示。** | 工具判断不了「用户需不需要」。把判定主体从「需不需要」（不可判定）换成「形式上违不违规」（可判定） |
| **P2** | ✅ **「脏」是形式属性，不是需求判断。** 「脏」的判定与「价值」的判定是分开的两句 | 这正是「会列出 Steam 库 + 告诉用户这是你的游戏 + 删除按钮就在那里」能自洽的原因 |
| **P3** | ✅ **不干预摆放。** 工具不提供「移动到正确位置」，只提供「删除 / 打开目录自行处理 / 归档」 | 摆放是用户的决定 |
| **P4** | ✅ **不作 remediation（不给「怎么改合规」）**，但**必须科普** | 见 §2.1 |
| **P5** | ✅ **LLM 只在用户主动触发时被调用**，永不自动扫描后送云端 | 隐私 |
| **P6** | ✅ **永久删除不可撤销性由用户承担**，但工具必须把证据摆在按钮旁 | 见 §6 |
| **P7** | ✅ **扫描必须由用户确认后执行**，默认值为 `$HOME`，且明显推荐用户自选目录 | 见 §7.2 |
| **P8** | ✅ **报告必须如实披露扫描盲区**（权限不足等） | 简报 §2.4 坑 1 的教训 |

### 2.1 P4 的取舍：为什么「不给建议」但「要科普」

用户否决了「告诉用户怎么改合规」（如留软链），理由是：

> **「留下软链接本身就是『脏』的一部分。」**

这个判断准确：软链会让账对不上（真实数据在别处，原位置留个指向），是**用一种脏替换另一种脏**。
所以不留软链、不建议 remediation，用户不想看见就直接忽略。

**但科普必须做，且要放在醒目位置**（用户明确要求），内容包括：
「为什么要保持目录干净整洁」「HOME 是哪里」「root 是哪里、都装了什么」「XDG 规范是什么」「不遵守 XDG 的应用会干什么」。

> **科普的正确形态**：不是抽象说明，而是**绑定用户自己的机器**——
> 「你的 HOME 是 `/home/xxx`，里面有这些…」「你装了 47 个应用，其中 N 个不遵守 XDG」。
> **教育靠呈现事实，不靠说教。**

## 3. 分类结构

### 3.1 ✅ 结构重构：「判脏的原因」与「操作流程」是两个维度

**这是本次讨论中我做的唯一一处结构性重构，请确认。**

原始表述（点 2 + 后续回答）里，「占用大 / 不符合规范 / 位置奇怪 / 孤儿可执行 / 缓存 / 说不清」是平铺的。
但这些不是同一个维度：「说不清」不是一种「脏」，而是一种**判定失败**——
它的处理流程（看内容 / 交 LLM）和其他类完全不同。

**建议拆成两个维度：**

```
判脏的原因（形式属性）              操作流程（谁来判）
├── 规范违规  NonCompliant          ├── 可直接判  → 三个操作
├── 位置异常  OddLocation           └── 需人工判  → 看内容 / 交 LLM
└── 体积异常  Large                     （= 「说不清」区）
判定失败
└── 说不清    Unclear
```

**「不整洁」= { NonCompliant, OddLocation, Large, Unclear }** —— 这四个是并列的进榜理由。

### 3.2 规范违规（NonCompliant）—— 关键：主语是「应用」不是「文件」

用户定位（C4）：

> 「XDG 是 GNOME、KDE、XFCE 等桌面环境的通用规范，GNOME 甚至全面遵守，
> 那这些应用想放哪里放哪里，本就是**极其野蛮**的行为。我们列出来，
> 不但是告诉用户『这个软件的开发者不重视你的用户目录干不干净』，
> 而且告诉软件开发者『**你不遵守规范我们就一直把你列出来**』。」

**所以这一栏的输出单元是「应用」，不是「文件」：**

```
Mojang —— .minecraft 放在家目录根
  XDG 建议: 配置 → ~/.config/minecraft，数据 → ~/.local/share/minecraft
  影响: 1 个目录 / 3.10 G
  [查看] [忽略]
```

**这个设计有个额外好处**：把矛头从「文件该不该删」转向「软件行为」，
**天然避开了 P1 的禁区**——它不评价价值，只记录行为。

**必须注意的边界（否则会变成大规模误报）**：
`.minecraft` `.steam` `.cargo` `.rustup` `.npm` **全都违反 XDG，且全都正常**。
本机实测：`.rustup` 1.6 G 看着像缓存，**实际是已安装的工具链本体**，删了 Rust 环境就坏。
→ **所以规范违规只登记、只点名，绝不产出删除建议。**

### 3.3 体积异常（Large）

- **只能对目录判定，不对散文件判定**（用户明确："文件管理器按大小排序时不会把文件夹大小算上"，而这正是本工具的差异化之一）
- 排序用**目录级别**的正确体积聚合

### 3.4 说不清（Unclear）—— 独立分区

**✅ 用户决策**：列一个「说不清」分区，**由用户决定是否丢给 LLM 判定，并警告这会消耗较多 token。**

**分区规模控制**：采用**自动预分组**（按所在目录 + 是否像应用数据聚类），
把上千条压成几十组，用户按组判断。**理由**：如果分区巨大，用户会直接全选删掉——这是最危险的结果。

**⚪ 级（无人认领）的统一提示文案**（用户指定）：

> **请「详细查看内容判断是否需要」或「交由 LLM 分析」**

**这条文案的设计意图**：它给出了**下一步动作**，而不是只给一个警告。
而且它天然接上 §5 的三个操作。

## 4. 引用证据（核心机制）

「它被谁谁谁引用了」是整个产品的论证支柱——**引用关系是唯一能强有力地回答「能不能删」的客观信息**。

### 4.1 ✅ 引用强度三级（用户确认）

| 级 | 判据 | 含义 | 证据强度 |
| --- | --- | --- | --- |
| 🔴 `InUse` | 进程 cwd / 打开句柄 | **现在删会出错** | 最硬 |
| 🟡 `WillUse` | 配置 / 桌面项 / 自启项 / 编排注册表指向它 | 下次启动会读 | 强 |
| ⚪ `Unclaimed` | 全系统零引用 | **≠ 不需要**，只是「无人认领」 | 弱 |

> **必须在数据模型里体现为三个不同的值，而不是一个布尔值 `has_reference`。**
> 否则以后想加回区分就要改核心。

**⚪ 级的教训来源**：简报记录的唯一一次事故，**恰好是一个零引用的空目录**——
它是另一套系统（harness）的运行目录，`find` 返回 0 条。**零引用不等于不需要。**

### 4.2 引用检查必须跨系统

必须查的「注册表」清单（与发行版无关）：

| 类别 | 查什么 |
| --- | --- |
| 进程 | 谁把它当 cwd / 打开句柄 |
| 包管理 | 哪个包拥有它 |
| 桌面集成 | 自启项、桌面项、菜单 |
| 应用自有 DB | 应用自己数据库里的路径记录 |
| **编排系统** | **工作区注册表、systemd unit、容器挂载、IDE 工作区** |
| Shell | 历史、rc 文件、定时任务 |

> **「这个目录是谁在用」是一个跨系统查询，不能只查文件系统。**

## 5. 交互模型

### 5.1 ✅ 每个条目三个操作（用户确认）

| 操作 | 说明 |
| --- | --- |
| **删除** | 永久删除 |
| **在文件管理器中打开目录自行查看 / 移动** | 工具不代劳摆放（P3） |
| **放到回收站归档** | 暂存，可按版本恢复 |

**✅ 明确的否定**：**不放说明文件到目标目录。**
理由：「他问了 LLM，那就让 LLM 告诉他怎么做；他不问就自己想放哪放哪，不规范再给扫出来。」

**这带来一个必须解决的问题**：用户一旦跳到文件管理器，**工具的证据就离开视野了**。
→ 证据的「跟手」问题仍未定（见 §8 待办）。

**✅ LLM 的建议可以点击固化保存**，以便用户随时查看。

### 5.2 回收站 = 归档，按版本管理

**✅ 用户强调（这是硬约束）**：

> **回收站中的归档按版本来管理，不能单个恢复。必须全量恢复、单次操作。**

**理由**：这是**结构性防误操作**——把「不要对单个文件操作」从**约定**升级成**物理不可能**。
因为「删哪个文件导致系统坏了」这个问题，**单文件级别的试错是不可取**的。

**LLM 在恢复中的角色（严格受限）**：

| 场景 | LLM 能做什么 |
| --- | --- |
| **应用起不来 / 某个功能坏了** | ✅ 告诉他**试着恢复哪个版本**，或者干脆全量恢复 |
| **用户数据丢了**（存档、文档、照片） | 🔴 **不许猜。** 只能建议全量恢复 |

> **区别在于**：应用坏了是**逻辑问题**（可推理）；数据丢了是**不可逆损失**（不能试错）。
> 把两者混在一个「让 LLM 挑」的入口里，风险很高。

**✅ LLM 在这条链路上的硬边界**：
- **不准执行任何操作**
- **不准对单个文件进行操作**

**如果用户想单独取某个文件**：自己去文件管理器里拿。
> **「这个我们也看不到，也不用看。用户自己的操作属于隐私。」**

### 5.3 恢复的实现约束（从「全量恢复」推导出的技术硬要求）

既然恢复只能整批进行，**任何「部分成功」都是不可接受的**：

> **恢复时若目标路径已存在同名文件 → 拒绝整批恢复，提示冲突，交由用户自行处理。绝不静默覆盖。**

否则「全量恢复」会产生**一半是新数据、一半是旧数据**的混合状态——比不恢复更糟。

## 6. 删除语义

### 6.1 两个按钮的分工

| | 永久删除 | 归档 |
| --- | --- | --- |
| 可撤销 | ❌ | ✅（按版本全量恢复） |
| 释放空间 | ✅ | ❌（取决于归档位置） |
| 用途 | 确定不要 | 暂存观望 |

**✅ 用户承担永久删除的后果**（「他知道了是 steam 库还删，这就没办法了」），
但 **P6 要求证据必须摆在按钮旁**——工具不阻止，但必须让用户是「知情」地删。

### 6.2 ✅ 归档空间的实现选择（用户选定）

- **同分区 rename** 为主 → 瞬间、不占额外空间、可撤销
- **专属空间** 作为「归档」形态

> ⚠️ **必须明确的后果**：如果归档是**同分区 rename**，那么「归档 20 G」之后 **`df` 不会少 20 G**。
> 用户会困惑「我清了啊，怎么没释放空间」。
> → **UI 必须把这个区别讲清楚**（「已清出视野」vs「已释放空间」）。

## 7. 扫描与隐私

### 7.1 ✅ 核心解耦：扫描范围与隐私无关

| | 是否受隐私约束 | 理由 |
| --- | --- | --- |
| **扫描范围** | ❌ **无关** | 纯本地只读，路径不出机器 |
| **送 LLM 的范围** | ✅ **受约束** | 只发生在用户点击「交由 LLM 分析」时 |

**推论**：
1. **扫描范围可以开得很宽**，不需要为了隐私而缩小——本地扫描越全，报告越诚实。
2. **扫描根是独立变量，不是 `$HOME`。** 不要用 `$HOME` 当默认根去推导隐私，否则两件事被绑死。

### 7.2 ✅ 隐私分级（用户选定）

- **目标在 `$HOME` 内** → 直接用 `$HOME` 形式发送，**不脱敏**
- **目标在 `$HOME` 外** → 明确告知：「**你选了 HOME 外的路径，我们需要提供完整路径上传给 LLM，请注意隐私**」，需用户确认

### 7.2b ✅ 排除清单：隐私项放到目标清理区域之外（用户选定）

用户原话（Q5）：「**怕隐私问题，就把隐私项目放到目标清理区域外。**」

**这不是提示，是机制** —— 扫描器必须有一份**默认排除清单**，这些路径
**既不出现在结果里，也永远不会被送进 LLM**：

| 类别 | 典型路径 |
| --- | --- |
| 密钥与凭据 | `~/.ssh`、`~/.gnupg`、`~/.password-store`、`~/.local/share/keyrings` |
| 浏览器配置 | `~/.mozilla`、`~/.config/google-chrome`（含 cookie / 登录态） |
| 令牌与云凭据 | `~/.aws`、`~/.config/gh`、`~/.docker/config.json` |
| 会话与历史 | shell history、`~/.dsh/sessions` 这类会话记录 |

**注意排除清单与 §3.1 的「说不清」分区的关系**：
排除是**在进榜之前**发生的，被排除的项**不进任何分区**，也不计入「说不清」。
否则用户会在「说不清」里看到自己的 `.ssh`，那等于把隐私问题又搬回来了。

**✅ 排除清单必须用户可见、可增删**（默认值只是起点）。

### 7.3 ✅ 扫描的执行方式（用户选定）

> **刚进去不要直接扫。默认是 `HOME`，需要点击确定执行。并在明显位置推荐用户选择目录。**

**理由**：扫描是用户主动发起的动作，默认值可接受即可，但必须显式确认。
配合 §2.1 的科普，**首次进入的界面 = 科普 + 目录选择 + 「开始扫描」**。

### 7.4 ✅ 信息透明清单（OOBE 必须写清）

用户要求：「我们所有能获取的信息范围、什么时候获取、信息用来干什么、会给到谁，**全部说清**。」

| 维度 | 内容 |
| --- | --- |
| **获取什么** | ① 只出本机：路径 / 体积 / mtime / 魔数 / 引用查询结果　② 送 LLM：脱敏元数据 + 系统上下文<br>**绝不发送文件内容**（除用户手动点击的单个小文本文件） |
| **什么时候** | ① 扫描时（只读，本机，需用户确认）　② **仅当用户触发 LLM 时**（不触发就不发） |
| **干什么用** | 生成「这是什么」一句话；**不用于任何自动操作** |
| **给谁** | 用户自己配置的 API 端点（**工具不做中转、不留副本**） |

**✅ 送 LLM 的系统上下文**（用户要求，帮助 LLM 判断目录结构、不至于瞎猜）：

```
发行版      Fedora 43 / UOS 20
桌面环境    GNOME / KDE / XFCE   ← 决定 XDG 遵守程度
包管理器    rpm / dpkg / pacman   ← 决定溯源查询方式
家目录      $HOME（脱敏为字面量 $HOME）
```

> **注意**：光知道发行版不够。**目录结构约定主要由桌面环境和包管理器决定**，不是发行版。

### 7.5 ✅ 扫描盲区必须披露（P8）

home 外读取会遇到权限不足。**扫描器必须记录「我没读到什么」并报告出来**，
否则会造成「这条覆盖了全盘」的错误印象。

> 这正是简报 §2.4 坑 1 的教训：`-maxdepth 4` 没扫到深层文件，却一度宣称「0 命中」。

## 8. LLM 的定位

### 8.1 ✅ 三层价值，基础层不依赖 LLM

用户选定：**「这是什么」列用明显标识告诉用户你没配置 LLM，那它只能按大小排个序。**
并指出这不只是残废模式：「**本来就认识这些文件的人**也能用——毕竟文件管理器按大小排序时不会把文件夹大小算上。」
「不配置 LLM 也可以当 BleachBit 的下位替代甚至平替。」

| 层 | 能力 | 需要 LLM |
| --- | --- | --- |
| **基础层** | 目录级体积正确排序 + 引用证据 + 规范审计 | ❌ |
| **鉴定层** | 「这是什么」自然语言解释 | ✅ |

**基础层是完整可用的产品**，不是阉割版。

### 8.2 ✅ OOBE 坦白（用户选定）

> **直接说清：这就是靠 LLM 清理的工具。怕隐私问题，就把隐私项目放到目标清理区域外，或者别用，或者自己部署 LLM。**

**这是一个诚实的定位，比偷偷摸摸好。**

### 8.3 ✅ 「这是什么」字段的内容（用户要求我补充）

用户给的原型：`.minecraft` → 「MC 游戏文件，由谁谁谁引用」。
注意其中**「由谁引用」是核心**——引用关系是唯一能强有力回答「能不能删」的客观信息。

建议每条目固定输出四块，**全部来自客观查询**：

| 块 | 内容 | 从哪来 |
| --- | --- | --- |
| **身份** | 目录/文件、体积、文件数、时间跨度 | 扫描 |
| **这是什么** | 一句话用途 + 依据（读到的关键文件 / 魔数） | 内容判定 |
| **归属** | 谁装的（包管理器 / 无）、谁生成的（构建系统 / 应用） | 溯源查询 |
| **引用** | 谁在用（三级强度，见 §4.1） | 跨系统查询 |
| **风险** | 删了会怎样（可重建？有唯一数据？） | 推断 |

**示例**：

```
身份   目录 · 3.10 G · 12,847 文件 · 2024-03 → 2026-08
这是什么  Minecraft 游戏数据（含存档、模组、资源包）
          依据: saves/ 目录 + mods/ + options.txt
归属   非包管理器安装（.local/share/hmcl 已不存在）
引用   🔴 无进程占用 · 🟡 无启动器引用 · 桌面项已失效
       🔴 saves/ 内 3 个世界存档无任何副本
```

> **最后一行是客观事实，不是替用户判断。** 用户看到「3 个世界存档无副本」，自己会决定。

**✅ 两条实现约束**：
1. **引用检查跨系统**（见 §4.2）
2. **不喂二进制给 LLM** —— 硬盘上多数体积是 ELF / 媒体文件，总结它们只会得到
   「这是一个 ELF 可执行文件」，**浪费 token 且零价值**。
   → **可读文本/配置走 LLM，二进制走「魔数 + 包管理器归属」。**

## 9. 技术选型

| 项 | ✅ 决策 | 备注 |
| --- | --- | --- |
| **语言** | **Rust** | 快速、安全 |
| **平台** | **先 Linux，之后可能 Windows** | 「Windows 已经有很成熟的清理工具」；**macOS 不做** |
| **GUI** | **先不做。先验证 core** | 用户选定 |
| **LLM** | **自定义 API**（用户自配端点） | 工具不做中转 |

**GUI 的技术建议（待定，非决策）**：点 5 的界面本质是**几千行列表 + 每行按钮 + 行内展开证据**——
虚拟滚动、行内操作在 web 前端是基本能力，在 egui/iced 里要自己写。
**若最终做 GUI，倾向 Tauri；但无论如何扫描核心必须做成独立 Rust crate + CLI/TUI**，
否则以后换 UI 要重写。

**已考虑但决定不加的功能**（参考其他管家应用的评估结论）：

| 常见功能 | 结论 |
| --- | --- |
| 系统监控 / CPU 内存仪表盘 | 不加，Stacer 已有，与本项目命题无关 |
| 启动项管理 | 不加，危险且红海 |
| 一键优化 / 一键清理 | **不加，直接违反 P1** |
| 权限审计 | 简报称真空、实测确实无人做，但**误报代价高**；本版不纳入 |

**唯一要加的**：**「我的盘到底被什么占着」**（用户选定）。
> 这不只是附加功能——**它是「整洁」框架的必要补充**。
> 光有「该删什么」会让人以为工具想删光他的盘；加上「你的盘被什么占着」才说明工具理解他有什么。

## 10. 数据模型草案（待实现时确认）

```rust
/// 引用强度：必须是三个不同的值，不能是 bool（见 §4.1）
enum LinkStrength {
    InUse,      // 🔴 进程 cwd / 打开句柄        → 现在删会出错
    WillUse,    // 🟡 配置/桌面项/自启/编排注册表 → 下次启动会读
    Unclaimed,  // ⚪ 零引用 → 文案:「请详细查看内容判断是否需要」/「交由 LLM 分析」
}

/// 判脏的原因（见 §3.1）
enum FindingKind {
    NonCompliant,  // 规范违规 —— 主语是「应用」，只登记不建删
    OddLocation,   // 位置异常
    Large,         // 体积异常 —— 只对目录判定
    Unclear,       // 判定失败 —— 独立分区，可选送 LLM
}

enum SharePolicy {
    InHome,        // 用 $HOME 字面量形式发送，需用户点击触发
    OutsideHome,   // 需显式同意：「位于 HOME 外，需上传完整路径，请注意隐私」
}

struct Finding {
    path: PathBuf,
    kind: FindingKind,
    evidence: Vec<Evidence>,    // 引用强度、包管理器归属、哈希、mtime、魔数
    scan_gaps: Vec<String>,     // ⚠️ 我「没读到」什么（权限不足等）—— P8 诚实性要求
    llm_share: SharePolicy,     // ⚠️ 隐私要求
}
```

> **注意 `scan_gaps` 和 `llm_share` 是两个独立字段**：
> 前者是**诚实性**要求，后者是**隐私**要求，**不要合并**。

**输出形态** ✅：**C 方案——JSON 为主数据 + Markdown 为渲染视图**。
> **JSON 的数据模型现在就应该固定**，因为它要为 UI 服务；
> Markdown 只是视图，可以随时改。

## 附：决策变更记录（讨论中被推翻的早期想法）

| 早期想法 | 最终决策 | 变更原因 |
| --- | --- | --- |
| 「LLM 总结」放在删除按钮旁作为主要依据 | LLM 只答「这是什么」；**证据才是按钮旁的依据** | 简报硬约束①：LLM 只输出判断+证据，且总结可能错 |
| LLM 默认全开 | **默认不调用**，用明显标识提示未配置 | 隐私；且基础层已可独立成立 |
| 给「怎么改合规」的建议（含软链） | **不给 remediation** | 「留下软链接本身就是『脏』的一部分」 |
| 目标 = 释放空间 | **目标 = 目录整洁**，空间是副产品 | Steam 库按空间是头号目标，按整洁根本不该进第一屏 |
| 「说不清」是低置信度的可持续处理区 | **是独立的判定失败区**，处理流程不同 | 它是「判定失败」，不是一种「脏」 |
| 隐私靠「缩小扫描范围」解决 | **扫描范围与隐私解耦**，只在送 LLM 时约束 | 本地只读不涉及隐私 |
| 回收站可单条恢复 | **按版本全量恢复，物理上无法单条操作** | 把「不要单文件操作」从约定升级成结构性不可能 |
| 「说不清」= 第 1 层、50–100 MiB 的目录（体积窄带） | **「说不清」= 无法确定性识别的条目（派生视图，与体积无关）** | 2026-10-20 实测：`large` 认领第 1 层 ≥100 MiB 后，体积窄带里永远没有条目 —— 该分区自 M1 起长期为 0，是**定义缺陷**而非数据巧合（见 [`DustLens-M5后测量.md`](./DustLens-M5后测量.md)） |
