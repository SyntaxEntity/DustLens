# M5 之后的残差测量 —— LLM 到底还有多少事可做

> 测量时间：2026-10-20 ｜ 测量对象：本机 `$HOME` 全量扫描（461 GiB / 105,331 目录 / 830,484 文件）
> 目的：回答「M5 内容鉴定做完之后，还需要 LLM 吗？」
> 所有路径以 `$HOME` 字面量表示，**不含真实家目录**。

---

## 0. 一句话结论

> **暂时不需要。** 残差里 85% 能被**再加几条规则**覆盖；
> 真正需要语义判断的可能只剩个位数条目，而 LLM 的调用成本低到不构成决策依据
> ——**问题不是贵，而是它要解决的那部分已经不多了。**

---

## 1. 测量方法

1. `dustlens scan "$HOME" --yes`（含去重、归属、失效引用、内容鉴定）→ JSON 报告
2. 统计各分区的条目数与体积
3. 对「体积异常」里**非确定性识别**的条目逐条取样，判断性质
4. 用一组**候选新规则**去覆盖这些条目，算出规则能做到多少

复现命令：

```bash
dustlens scan "$HOME" --yes -o /tmp/m
# 然后对 /tmp/m/*.json 统计 evidence 里 kind == "identification" 的条目
```

| 分区 | 条目 | 说明 |
|---|---:|---|

## 3. 🔴 重要发现：「说不清」分区是**结构性为空**的

### 现象

M5 之前之后，这个分区在本机都是 **0 条**。

### 原因（读代码得出的，不是猜）

```
large  的候选：扫描根 + 第 1 层 + 第 2 层，门槛 ≥100 MiB
unclear 的候选：仅第 1 层（parent == 扫描根），门槛 ≥50 MiB，且「未被 large 认领」
```

→ **第 1 层 ≥100 MiB 的目录全被 `large` 拿走**，`unclear` 只剩下
「第 1 层、50–100 MiB」这条窄带。这台机器上那条带里恰好一个都没有。

### 后果

「说不清」作为产品概念目前是**死的**：它永远不会装下真正需要人判断的东西，
因为那些东西一旦够大就先进了「体积异常」。

### 结论

这不是数据问题，是**分区定义问题**。若保留这个概念，定义应改为
**「未被确定性识别」**（与体积无关），而不是「50–100 MiB 的窄带」。

## 3.5 ✅ 后续处理（2026-10-20 同轮完成）

按 §7 的建议 1+2 已实施：

1. **「说不清」改为派生视图**：`unclear = 体积异常/位置异常里无法确定性识别的条目`，与体积解耦。
2. **补了 R1–R7 规则 + 扩展名下探到两层 + 动态应用名规则 + 项目集合判定**。

修复后同一台机器的对比：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 确定性识别 | 9 | **52** |
| 「说不清」条目 | **0**（结构性为空） | **10** |

剩下的 10 条里，9 条是 ≤1 GiB 的小目录，只有 `$HOME/Documents/远古遗迹`（9.7 GiB）
是真正需要语义判断的 —— 与本节「个位数」的预测一致。

## 5. 那 53 项「没认出来」的到底是什么

### 5.1 加上 7 类候选规则后

| 候选规则 | 覆盖 | 体积 |
|---|---:|---:|
| R1 XDG 容器 / 用户标准目录 | 16 | 525 GiB |
| R2 工具链 / 包管理器（`.rustup` `.cargo` `.npm`…） | 7 | 5.9 GiB |
| R3 Qt SDK（`Qt/*`） | 4 | 5.4 GiB |
| R4 IDE 安装（`qtcreator-*`、JetBrains Toolbox） | 4 | 1.5 GiB |
| R5 已知应用数据（`.codex` `.xwechat` `.config/QQ`…） | 7 | 4.6 GiB |
| R6 缓存目录（`.cache/*`） | 5 | 6.1 GiB |
| R7 游戏安装（`Games/*`） | 2 | 185 GiB |
| **合计可覆盖** | **45 / 53** | **734 / 831 GiB（88%）** |

### 5.2 规则覆盖不到的 8 项（45 GiB → 实际 97.4 GiB）

| 条目 | 体积 | 为什么规则难覆盖 |
|---|---:|---|
| `$HOME/Documents/A408` | 79.6 GiB | 媒体藏在**两层**之下（`A408/武忠祥…/视频/*.mp4`）；扩到两层下探即可 |
| `$HOME/Documents/远古遗迹` | 9.7 GiB | 名字是语义性的，只能靠人/LLM |
| `$HOME/Documents/xwechat_files` | 5.7 GiB | 名字规则可覆盖（微信文件） |
| `$HOME/UCAS`、`UCAS/website` | 1.4 GiB | 项目容器；结构标记在更深层 |
| `$HOME/Projects/QtAdb`、`RustroverProjects` | 0.9 GiB | 同上 |
| `$HOME/Applications` | 0.2 GiB | 容器目录 |

**把「扩展名下探」从 1 层扩到 2 层 + 加一条「项目容器」判定后，
真正只剩 `远古遗迹` 这一类（个位数条目）需要语义判断。**

## 6. LLM 的账

### 6.1 需要它的条目有多少

| 条件 | 条目 | 体积 |
|---|---:|---:|
| 弱识别 / 未识别（排除扫描根） | 53 | 831 GiB |
| 其中**无人认领** | 24 | 219 GiB |
| 扣除 XDG 容器后（真正的语义候选） | **个位数** | ≈ 10 GiB |

### 6.2 成本估算

| 每条 payload | 24 项合计 |
|---|---:|
| 150 tokens（路径+大小+mtime+20 个子项名+魔数） | ≈ 3,600 |
| 300 tokens | ≈ 7,200 |
| 600 tokens（再带一个代表文本文件的前 4 KiB） | ≈ 14,400 |

**成本低到不构成决策依据**（一次全盘扫描的 LLM 账单约几分钱）。

### 6.3 所以结论不是「太贵」

> **结论是：M5 之后，需要语义判断的东西已经少到不值得为它建一整套 LLM 管线**
> （配置端点、隐私确认、token 计量、结果缓存、失败降级…）。

## 7. 建议的下一步（按价值排序）

| 优先级 | 事项 | 理由 |
|---|---|---|
| **1** | **修正「说不清」的定义**：改为「未被确定性识别」（与体积无关），并让它真正能包含大条目 | 否则这个概念在产品里是死的；这也是唯一会让 LLM 有意义的入口 |
| **2** | **补 R1–R7 七类规则 + 扩展名下探到 2 层** | 一次投入覆盖 88% 的残差，且**零运行成本、零隐私风险** |
| **3** | 重跑本测量 | 若残差 < 5 项，则 M6 只剩「锦上添花」；若仍多，再上 LLM |
| 4 | M6 LLM 层 | 按设计共识它本就是「最后一块拼图」 |

## 8. 复现与验证

```bash
# 1. 扫描
dustlens scan "$HOME" --yes -o /tmp/m

# 2. 分区计数
python3 - <<'PY'
import json,glob
d=json.load(open(sorted(glob.glob('/tmp/m/*.json'))[-1]))
for k in ('large','odd_location','unclear','dangling','non_compliant'):
    print(k, len(d[k]))
PY

# 3. 鉴定覆盖
python3 - <<'PY'
import json,glob
d=json.load(open(sorted(glob.glob('/tmp/m/*.json'))[-1]))
for k in ('large','odd_location','unclear'):
    for x in d[k]:
        ids=[e for e in x['evidence'] if e['kind']=='identification']
        print(x['display_path'], '|', ids[0]['what'] if ids else '无鉴定',
              '|', 'confident' if ids and ids[0]['confident'] else 'weak')
PY
```
